# 客户端开源方案

## 发布边界

公开一份能独立运行的完整客户端，不把官方业务服务一起开源。建议新建公开客户端仓库，账户后台和官网继续放在私有仓库或私有工作目录中，分别维护与部署。

公开客户端仓库：[ponysb/mlimli](https://github.com/ponysb/mlimli)。客户端根许可证采用 Apache-2.0，第三方内容保留原有许可证。

### 公开的内容

- `react/`：完整工作台源码、样式与客户端品牌资源。
- `core/`：Agent 循环、模型适配、会话、权限、项目记忆、资源、专家、Skill 和扩展代码。
- `server.mjs`：本地 HTTP / SSE 服务。它是客户端的一部分，不能因文件名含 server 就删掉。
- `electron/`：桌面入口、预加载桥与图标。
- 明确列出的内置 `plugins/`：执行工具与随客户端附带的第三方工作流 Skill，包括已有第三方通知。
- 客户端测试、自检、依赖锁文件、构建配置和无凭据启动示例。
- 客户端调用官方账户、模型目录和插件服务的代码可以公开；接口客户端并不等于服务端实现。

### 不公开的内容

- `server/`：数据库模型、认证服务、支付回调、账户管理、模型网关、后台控制台、私有配置与存储。
- `server/website/`：官网页面、插画、样式、目录与托管逻辑，随私有后台部署。
- 真实 `config.json`、任何真实 `.env`、数据库/支付/邮件配置、服务端共享密钥和上游 API Key。
- `.agent/`、会话、记忆、权限规则、素材、日志、用户工作区与系统用户配置目录里的账户凭据。
- 私有 Git 历史、`node_modules/`、现有 `dist/` 与后台构建产物。
- 个人安装的 Skill 或平台内容不自动转为开源授权；导出只包含已列出的客户端内置插件。

**功能完整不等于把业务服务附带出去。** 开源用户可用自己的模型服务运行 Agent 和本地工具；官方账户、充值、云端模型网关和平台内容仍依赖运营方的私有服务。客户端不会附带这些服务的数据库或实现，也不会把付费平台内容自动复制给公众。

## 生成独立客户端源码

在内部工作目录执行：

```sh
npm run export:client -- --dry-run
npm run export:client
```

默认生成 `release/client-source/`，也可指定一个新的空目录：

```sh
npm run export:client -- --output ../mli-client-public
```

导出工具的约束：

1. 使用文件和目录白名单，而不是复制全部文件再删除后台。
2. 不读取真实运行配置，只发布 `config.example.json`，并默认关闭官方账户要求。
3. 过滤运行数据、环境文件和私钥文件；拒绝允许范围内的符号链接，避免通过链接带出目录外内容。
4. 只保留客户端 npm 脚本；移除官网、私有后台启动和后台插件发布脚本。保留客户端依赖锁文件。
5. 做已知 Key 格式和私钥块的基础扫描，命中时拒绝导出，不在控制台打印凭据正文。
6. 输出 `EXPORT-MANIFEST.json`，列出相对路径、字节数和 SHA-256，方便比较每次候选发布的文件。
7. 不覆盖非空目录，不执行 Git 初始化、提交、推送、上传或 npm 发布。

基础扫描无法识别所有类型的敏感数据，也不能判断素材著作权。**导出清单仍需人工核对。** 添加新插件或目录时，应先审核内容、外部依赖和许可证，再修改导出白名单，不要为了省事放开整个项目目录。

## 首次公开发布

1. 先导出到新目录。不要将现在的混合开发目录或其历史直接改为公共仓库。
2. 检查 `EXPORT-MANIFEST.json`：不应出现 `server/`、`website/`、真实配置、会话或日志。搜索个人路径、账号、非公开服务地址和凭据；清理误植在源文件或文档里的内容。
3. 保留根目录 `LICENSE`，并核对 `package.json` 和锁文件的根许可证均为 Apache-2.0。不要覆盖第三方文件已有的许可证或归属声明。
4. 核对每个第三方插件的来源、manifest 许可、已有许可证与 `THIRD-PARTY-NOTICE.md`；需要保留的原始许可和通知必须一起保留。品牌名称、商标、插画、字体与服务凭据不能仅凭代码许可证自动推定可授权。
5. 在导出目录 `npm ci`，复制安全示例配置，执行 `npm test`、`npm run check` 和 `npm run build:web`；启动本地 mock 工作流，再用测试用的自带模型验证实际接口。不要在公开测试日志里输出真实 Key。
6. 确认没有私有代码后，才在**导出的目录**初始化独立 Git 仓库并关联公共远程。公开 README、许可证和客户端源码，不上传内部目录。
7. 公共仓库地址、发行下载与安装包准备好后再填写 README，不使用占位链接冒充已经发布。

如果私有文件曾经进入已有 Git 历史，新增 `.gitignore` 或删除当前文件并不能清除历史内容。最简单的边界是从审核后的导出目录建立全新公开仓库；已泄露凭据应先撤销或轮换，再处理历史副本。

## 后续维护

- 内部混合目录继续开发，公开客户端仓库单独管理 Issue、贡献与发行版本。
- 每次导出到新的空目录，对比清单和公开仓库，再审核客户端补丁；不要复制私有目录覆盖公开仓库。
- 来自公开仓库的客户端改动可以同步回内部客户端代码；后台和官网不需要跟着公开，也不接受通过客户端补丁引入服务端秘密。
- 将“导出测试 + 客户端测试 + 自检 + 构建”作为发布门槛。发布安装包时，应从审核后的公开源码重新构建，而不是直接上传包含私有路径或配置的内部产物。

## 官方服务与安全

公开客户端不能可靠地保守长期共享密钥。不要把 `MLI_ACCOUNT_APP_SECRET`、支付签名密钥或模型网关的上游 Key 固定在客户端里。

自带模型模式默认关闭账户限制，并由用户自行配置供应商。若需要官方模型、充值和插件中心，客户端连接运营方发布的服务地址；身份校验、余额校验和托管模型的最终结算由私有服务端负责。客户端源码公开不改变服务端对用户权限的校验。

本地 Agent 服务用于单用户本机运行，不是部署到公网的业务后台。贡献者测试时应使用专门工作目录和无敏感资料的账户。

## 发布约定

公开仓库只接收审核后的客户端导出内容；内部混合目录不会直接推送。源码推送与安装包发行分别进行，仓库地址不代表已经上传安装包。每次同步应保留公共仓库现有历史，不使用强制推送覆盖社区贡献，并再次执行范围检查、客户端测试、自检与构建。
