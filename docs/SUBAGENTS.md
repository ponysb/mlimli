# 子 Agent 协作

## 当前实现：分层蜂群与安全接续

本节描述最新行为，后续带日期的内容保留历史参考。

- 主 Agent 用 `agent_mission` 保存目标和稳定要求 ID；任务用 `requirementIds` 关联要求。验收设为 `accepted` 时必须填写证据，未验收要求阻止正常完成。证据内容仍需真实核查，程序不自动证明语义正确。
- `canDelegate: true` 创建范围负责人，负责人可继续派发下属并接收其成果；默认最多三层，`maxDepth` 可配置为 1–8。普通叶任务不能派发，下属工具和只读约束继承父任务限制。
- 负责人只等待下属，不等待祖先或同级；等待时让出全局执行容量，继续推理前重新领取。停止负责人取消整条后代分支，无关范围继续执行。范围文字是任务契约，尚无逐文件所有权强制机制。
- 目标、任务图、邮箱和历史尝试保存为 `.agent/task-groups/<rootSessionId>.json`，临时文件 fsync 后原子替换；旧 JSONL 可读取。当前采用单运行时状态快照，未实现 SQLite 事务／分页任务存储。
- 启动当前工作区时自动发现未完成蜂群，恢复尚未执行的任务及没有未知副作用或外部句柄的检查点。已完成成果保留；外部 ACP、未知副作用操作或缺少检查点的执行进入中断／需核对状态，不自动重放。旧任务组不自动迁移为可恢复任务。
- 关闭最后客户端时，正在执行或等待审批的任务保持本地后端存活。正常服务退出保留恢复状态；明确停止取消任务。系统关机期间不运行，重新启动应用后才恢复；未安装系统自启动服务。仅当前工作区自动恢复。
- 编辑器原状态标签向上展开非模态浮层，展示任务层级、范围负责人、等待下属、恢复和目标验收状态；会话布局保持不变。
- 具备 write 能力的文件任务可声明 `writablePaths` 进入独立快照；多个不同文件范围可并行。完成后直接负责人用 `agent_integrate` 接收，主目录基线变化会显示冲突并停止合入；未接收交付不能作为下游依赖的正式输入。共享目录任务仍串行。

新增接口：`GET/POST /api/session/:rootId/mission`。模型工具 `agent_mission` 无参数读取，带 requirements 更新。用 `agent_inspect` 查看整个蜂群与恢复阻塞。

隔离交付保存文件基线 hash、权限和不可变暂存字节，先全量检查冲突，再逐文件原子替换。多文件合入不是单个原子事务；故障时保留 applying 日志，重试跳过已应用文件，若外部再次修改则停止并返回冲突。完成的隔离任务需重新创建任务才能修改，以建立新基线。快照最多 128MB／20000 文件，单文件最多 16MB；排除私有目录、依赖和构建目录，不支持 shell／ACP 进程隔离。

`adaptiveConcurrency: true` 可启用自适应容量，从最多 2 槽开始，在用户 maxConcurrent（最高 8）内逐步增加；遇到 429／限流减半，冷却 30 秒后依据成功恢复。默认关闭，固定容量行为保持。浮层显示当前容量和待接收成果数。

尚未实现：多机执行、OS 后台服务、整组费用硬预算。已增加24任务三阶段真实模型进程崩溃恢复基准；它验证批量调度与接续，不代表任意大型任务质量或通宵稳定性。

## 2026-10-19 动态蜂群更新

新派发协议已移除固定四角色：主 Agent 自由定义每项任务的 `role`、`scope`、`acceptance`，按需组合 `capabilities: ["read", "web", "command", "write"]`。能力是工具权限分组，不是角色模板；每项任务拥有独立上下文和结果交接。写入能力仍受父任务授权、审批及共享目录互斥约束。旧 `profile` 参数仅兼容历史客户端和保存记录，不再出现在模型工具协议中。通用模型与预算设置使用 `agent.subagents.modelId/maxSteps/maxDurationMs/prompt`。

UI 沿用编辑器内原有状态小标签：点击在标签上方展开紧凑蜂群浮层，查看状态、任务、依赖与活动；点击外部收起，会话页面保持可操作。它不再是全屏遮罩工作台。

下文提到固定四角色和 profiles 配置的部分是旧版本历史；新任务应使用上述动态协议。分层派发、安全重启接续、隔离并行文件交付已实现，当前限制见文首。

MLI Agent 支持一个主任务调度多个具有独立上下文的子 Agent。子 Agent 在同一个 Node.js 运行时中异步执行，各有独立 Session、模型请求、上下文压缩、取消信号和历史文件。它们共享工作目录，因此上下文隔离不等于文件隔离。

## 从哪里启动

接入支持工具调用的真实模型后，默认采用主动派发策略。复杂任务中有可独立调查的模块、来源或验证方向时，主 Agent 会被引导主动拆分，不需要用户每次写「启动子 Agent」。例如直接提出：

> 分析这个项目的登录流程、错误处理和测试缺口，给出证据并完成必要的修复。

主 Agent 可以按不同模块并行探索，保留全局决策，修改稳定后再安排独立审查。单文件小修改或简短问题仍直接完成。是否派发由模型根据任务、工具和指令判断，运行时不通过关键词强制启动；实际派发质量仍需要真实模型任务评估。

也可以明确指定分工：

> 启动两个子 Agent：explorer 检查登录模块的调用链，reviewer 检查异常处理和测试缺口。都只读，附文件位置与证据。你负责汇总并验证结论。

模型通过 `agent_spawn` 的 tasks 数组批量派发独立分支，立即取得任务句柄并继续其他工作。初始建议 2–3 个清晰分支，调度器仍遵守全运行时的并发上限，不为凑数量拆出微小任务。子任务返回结果后，主 Agent 检查证据、处理冲突并运行必要验证。

会话中的「蜂群」入口只在实际产生子任务时出现，打开蜂群工作台后可查看执行、排队、需关注和已结束数量，以及任务、依赖、活动三个视图。工作台支持搜索、状态筛选和分批展示；详情包含范围、验收条件、排队原因、历史轮次、模型、tokens、结果和停止操作。用户无需选择角色或填写派发表单；调整目标直接在主任务中提出，由主 Agent 决定如何调整、补充或停止子任务。

**左侧会话列表默认只显示主任务。** 点击面板内的子任务可查看其独立历史，再点「返回主任务」。子任务没有普通消息输入框，统一从主任务追加指令。

修改源码后运行 `npm run build:web`，再重启运行时；已经运行的服务不会自动加载内核修改。示例配置中的 mock 模型可用「使用子 agent 并行探索」演示两任务协作，但不会进行真实代码分析。

## 旧版角色和授权（历史参考）

- `explorer`：只读代码与文件探索，可在只读沙箱中执行命令。
- `researcher`：只读资料研究，可读取文件和抓取网页。
- `reviewer`：只读审查，可在只读沙箱中执行验证命令。需要写缓存或生成文件的测试应交给主 Agent。
- `worker`：读取及修改文件；本版不开放 shell、通用 MCP 或桌面操作。

角色工具权限同时在模型可见工具列表和实际执行入口检查。子 Agent 继承派发时主任务的审批模式，角色限制及沙箱不会被审批放宽。子任务的审批和提问会汇集到主任务，响应仍发送给实际来源会话。

共享目录只允许一个子 worker 执行；期间主 Agent 的修改、命令及其他受保护操作会被阻止，需等待 worker 完成。已在执行的主工具持有资源租约，worker 会等待它结束。只读 Agent 可并行，但可能观察到其他任务正在修改的文件；需要一致的输入时，用依赖安排先后顺序。

## 启动、通讯和停止

运行时提供以下编排工具（另有 agent_mission 和 agent_integrate）：

- `agent_spawn`：异步派发，返回 taskId、agentId 和状态；一次 1–8 个任务，可分批持续扩展。可用 idempotencyKey 防止重复派发，dependsOn 指向同组已有 taskId 或同批任务 ref，支持前向引用；派发前拒绝缺失和循环依赖。scope、acceptance 分别描述负责范围和验收条件，下游执行时接收上游成果摘要与产物引用。
- `agent_send`：向指定 agentId 发消息；`steer` 在下一模型／工具边界生效，`info` 提供资料，`follow_up` 让已结束的子任务明确续跑。不会中途修改正在执行的工具参数。
- `agent_wait`：等待 any/all，遇到子任务审批或输入请求可返回；单次最长等待 45 秒，超时不代表任务失败，可携带 afterRevision 等待状态变化。
- `agent_inspect`：读取状态、使用量和结果证据，不默认复制完整子会话历史。
- `agent_stop`：停止指定子任务，包括取消排队、执行及待审批。

主 Agent 和明确获得 canDelegate 的范围负责人可派生子任务。下属向直接负责人交接，负责人可联系自己的后代；暂不开放同级互发。消息持久化并按 messageId 去重，在安全边界消费，内容标记为协作资料，不能作为新增用户授权。

主任务可在一个分支返回后继续推理、消费成果并派发后续任务，不必等待其他独立分支；完成最终回复前仍等待其所有未结束子任务。停止主任务会取消整组任务；子任务失败会阻止依赖它的任务启动，主 Agent 应说明失败和验证缺口。已结束任务追加要求会保留上一轮结果；存在下游依赖的上游任务不能原地续跑，应派发新任务明确表达新的依赖版本。

运行时重启后先将未结束任务标记中断，再对新版任务组执行恢复检查。未执行任务与安全检查点可自动接续；未知操作、外部执行和旧版任务组保留中断，核对后由主任务重新派发。普通已结束任务在同一运行时内可追加要求。

## 配置

在 `config.json` 的 agent 中配置，修改后重启：

```json
{
  "agent": {
    "maxSteps": null,
    "maxDurationMs": null,
    "subagents": {
      "enabled": true,
      "delegation": "auto",
      "maxConcurrent": 2,
      "maxTasks": 512,
      "profiles": {
        "reviewer": {
          "modelId": "your-review-model-id",
          "maxSteps": null,
          "maxDurationMs": null,
          "prompt": "重点检查异常路径，报告附文件位置。"
        }
      }
    }
  }
}
```

`delegation` 控制模型的协作提示策略：`auto`（默认，旧配置没有此字段时同样生效）要求主模型评估任务，遇到值得并行的独立分支或必要的独立审查时自行选择角色并派发；`on-request` 指导模型仅在用户明确要求多 Agent／并行 Agent 时派发。它是模型行为指导，不是确定性的任务分类器。`enabled: false` 会隐藏编排工具并拒绝派发。用户当前要求串行或禁用子 Agent 时，主模型应遵从。

modelId 对应已配置模型的 id，省略时继承主任务派发时的模型。运行中的模型选择保持固定，切换全局模型不会改变已经启动的任务。各角色可指定模型、补充提示和预算，不能扩大内置工具权限。探索可手动配置响应较快的模型，重要审查可选更强模型；本版不会自动判断服务商中哪个模型更快或更便宜。

默认同时运行 2 个子 Agent，全运行时最大可配置到 8；此限额不包含主 Agent，排队中的任务尚不发起模型请求。派生深度默认 3、最高 8，每组累计任务容量 maxTasks 默认 512，最高 10000；总任务数与同时运行数分别限制。主任务与子任务默认不限制总轮数或运行时长；示例中的 maxSteps 和 maxDurationMs 仅表示用户可选预算，null 表示不限制。显式预算覆盖实际循环，达到限制会显示「达到预算」。目前未实现整组 token／金额硬上限，增加并发可能增加模型费用。

## 存储和接口

Session 历史保存在工作目录 `.agent/sessions/`，子会话包含 parentSessionId 和 rootSessionId。组状态、邮箱及幂等记录保存在 `.agent/task-groups/<rootSessionId>.jsonl`，较大的重复快照会压缩为最新快照。API 日志记录 agentId、taskId 和 rootSessionId，子任务使用量按货币分别累计。

主要 HTTP 接口：

```text
GET  /api/agent-profiles
GET  /api/session/:rootId/agents
POST /api/session/:rootId/agents
POST /api/session/:rootId/agents/:agentId/message
POST /api/session/:rootId/agents/:agentId/stop
```

派发请求格式与 agent_spawn 相同，响应为 202 和任务句柄。查看主会话时包含 group、permissions 和 uiRequests；处理审批使用请求自己的 sessionId。子会话普通发消息、排队、切换权限／专家／桌面功能的入口会拒绝操作。

## 本版范围与验证

已实现独立上下文、角色限制、异步派发、并发调度、依赖、邮箱、结果汇总、整组取消、重启恢复和工作台内的子任务面板。CLI 可处理来自子任务的审批，但尚无专门的子任务导航命令。

自动测试覆盖两个 mock 子任务真实时间重叠、历史／模型／路径／日志隔离、幂等与消息去重、审批来源、只读工具防绕过、资源租约、步骤预算、取消和重启不重放。2026-10-03 全量测试 147 项通过、1 项跳过，运行时自检及 Web／TUI 构建通过；最终面板调整后的相关 18 项测试再次通过。独立 Electron mock 环境确认左侧仅一个主任务、面板内两个子任务、主子历史切换、四个派发角色、折叠的协作消息以及滚动时面板可见。尚未进行真实服务商的质量、成本和吞吐量基准。

后续扩展包括 Git worktree 隔离下的并行实现、独立产物目录、团队 token／金额预算、同级通信、长期 Worker 与多进程后端。本版不自动创建 Git worktree，也不具备长期蜂群团队的完整调度能力。

## Cursor 方案参考

2026-10-04 核对 [Cursor 官方 Subagents 文档](https://cursor.com/docs/subagents) 后，补充默认主动派发提示、角色选择依据、批量并行探索、控制分支规模与独立审查。Cursor 同样由主模型根据任务复杂度、角色描述、上下文和工具主动决定派发；独立上下文保留中间日志，只回传结果。本版沿用这些机制，保留既有审批和单写入者限制。

本次改动后再次运行全量测试：147 项通过、1 项跳过；运行时自检通过。补充检查主动派发、按请求派发、禁用、工具不可见和子任务契约的策略分支。真实模型的自动派发频率及加速效果尚未测评。

Cursor 文档还包括内置 Explore／Bash／Browser、前台与后台、文件定义的自定义角色、受限嵌套以及隔离项目副本。这些不等于本版已经完整支持：旧版全部异步派发，角色曾为固定四类；当前已由动态职责替代。旧版没有专用 Browser Agent、任意 shell Worker、自定义角色文件加载或自动 worktree。

[Cursor 的长期多 Agent 研究](https://cursor.com/blog/scaling-agents) 使用规划者、执行者和周期验收者来协调大型项目。它是研究系统，不能直接当作普通聊天中的自动子 Agent 的全部实现。本版优先采用主任务负责整合、短任务子 Agent 负责明确分工的结构。
